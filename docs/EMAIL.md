# Transactional email — Resend preparation

## Current and target architecture

Supabase Auth owns accounts, signup confirmation, password login, sessions, and LINE OAuth. Signup confirmation and password recovery are implemented on the deployed staging app. Magic link, invitation, and email-change UI are not implemented. Local Supabase routes confirmation email to Inbucket. Hosted staging Auth invokes the Resend hook; the user confirmed signup/confirmation, recovery, login/logout, LINE, session persistence, and staging-only redirects after the HTTPS deployment.

Staging uses a Supabase Send Email Auth Hook (`supabase/functions/staging-send-email`) with a strict recipient allowlist and the Resend API. Production Supabase Auth uses Resend SMTP without this hook. Future application transactional mail calls `lib/email/service.mjs` on the server. There is no marketing mail, public send-email endpoint, email table, or webhook in this MVP.

The sender is `LangsuanApp <no-reply@auth.langsuanapp.com>` on the verified Resend sending domain. A separate sending domain can be added later for non-Auth messages.

## Non-secret configuration and secrets

`config/*-parameter.conf` declares `EMAIL_PROVIDER`, `EMAIL_ENV`, `EMAIL_FROM_NAME`, and `EMAIL_FROM_ADDRESS`. Staging also declares `EMAIL_ALLOWED_RECIPIENTS=none`, which intentionally blocks all application-generated mail until replaced with an explicit comma-separated list of test addresses. Local follows the same fail-closed rule. Production must not have a recipient restriction. The service rejects missing/invalid configuration and missing `RESEND_API_KEY` without contacting Resend. It logs provider, type, environment, outcome, timestamp, message ID or failure category, never recipients, body, API key, or Auth links. It retries network errors, HTTP 429, and 5xx at most twice using a stable idempotency key; permanent errors are not retried. A durable queue may be added only when actual application notifications require one.

Store `RESEND_API_KEY` only in ignored `.env.local` for local development, in the Cloudflare Worker secret store for runtime application email, and in GitHub Environment secrets if CI requires it. The key value must never enter `NEXT_PUBLIC_*`, parameter files, Git, browser bundles, or logs. The Production Auth SMTP password is configured directly in Supabase with a dedicated Resend sending key distinct from the Worker API key. The production workflow requires its GitHub Environment `RESEND_API_KEY` secret before building/deploying; this is a gate, not proof that the Worker runtime secret is installed. Use `wrangler secret put RESEND_API_KEY --name lang-suan-staging` only when staging is ready to send application mail.

No SPF or other conflict existed. These four records were created without modifying or deleting unrelated records; a repeated Cloudflare audit found all four unchanged. Resend subsequently reported the domain and all four records `verified`. DMARC remains unconfigured.

2. With a temporary Resend Full access key (Sending access cannot read domains) and a Cloudflare token scoped to **only** the `langsuanapp.com` zone with DNS Read, run `node scripts/resend-dns.mjs audit`. 3. Review every proposed record, especially any SPF or DMARC already present. The script refuses conflicting SPF, DKIM, MX, or CNAME records rather than overwriting them or creating a second SPF. Add a reporting address only when a monitored mailbox exists. After observing alignment and legitimate traffic, tighten to `quarantine` and later `reject` through a separate reviewed DNS change. The script does not create DMARC automatically.

## Staging Auth Hook and password recovery

The staging-only Edge Function checks its built-in Supabase project URL and `APP_ENV=staging`, verifies the Supabase Standard Webhooks signature, parses `STAGING_EMAIL_ALLOWLIST` strictly, checks the signed recipient against the allowlist, and rejects missing/malformed settings before sending. Only `signup` and `recovery` are enabled; magic link, invitation, and email change fail closed until separately designed and tested. It checks the signed redirect origin, then generates confirmation/recovery links exclusively on `https://staging.langsuanapp.com`. The signed `site_url` is diagnostic-only because live staging requests supplied an origin different from the verified remote Auth Site URL; it is never used to construct an email link. Supabase PKCE requests prefix the token hash with `pkce_`; the hook accepts that exact prefix plus the existing hexadecimal hash format, preserving the signed hash unchanged in the staging link. It logs only a coarse Site URL category, never addresses, URLs, tokens, links, or secrets. An error is returned to Supabase rather than falling back to default SMTP.

No automated test sends actual Production email. The Staging recipient guard remains isolated; Production uses normal SMTP with no Staging Auth Hook. DMARC is still absent and requires a separate monitoring-policy decision after sender inventory.

## Troubleshooting and rotation

For a failed app email, inspect structured logs by environment/type/category/message ID and Resend's delivery dashboard. `configuration` means missing key/sender or provider access; `recipient_blocked` means staging guard; `invalid_recipient` is permanent; `rate_limit` and `temporary_delivery` receive bounded retries. Do not dump provider responses because they may contain addresses or message content. Staging Auth Hook failures are diagnosed in Supabase Auth/Edge Function logs and Resend delivery logs; never log confirmation links or tokens.

To rotate: create a new Resend sending key scoped to `auth.langsuanapp.com`, update the staging Edge Function `RESEND_API_KEY` secret, test an allowlisted recipient, then revoke the old key. Rotate the Supabase hook signing secret in its Auth Hook configuration and Edge Function secret together, allowing documented overlap only if supported. The tracked `supabase/config.toml` intentionally omits the hook's secret-bearing config: the CLI validates it even during function deploy and refuses an unresolved `env(SEND_EMAIL_HOOK_SECRET)` reference. Keep the remote hook configuration separately managed until a secure, available config secret source is established. Production SMTP rotation is a separate future operation after production activation. Never paste keys into docs or GitHub logs. Webhooks are deferred until bounce/complaint handling is a real operational need; any future `/webhooks/resend` endpoint must verify Resend's current signature mechanism before trusting payloads.
